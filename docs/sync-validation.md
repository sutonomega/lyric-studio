# Lyric Studio 歌詞同期の技術検証計画

2026-11-24 / レビュー案 / [承認・変更管理 #1](https://github.com/sutonomega/lyric-studio/issues/1)

## 検証する仮説

入力歌詞を使った順序制約付きの照合で、実際の日本語Suno楽曲に手動より少ない作業で字幕を付けられるかを測る。ボーカル分離と境界の強制アライメントは、同一曲での改善と処理コストで判断する。

## 比較条件

| 条件 | 入力と方式 | 比較対象 |
| --- | --- | --- |
| A | 原音＋faster-whisper（日本語、時刻付き）＋動的計画法 | 基準 |
| B | htdemucsのボーカル＋Aと同じASR・照合 | Aとの差で分離の効果を測る |
| C | AまたはBの暫定行位置＋区間別の日本語CTC強制アライメント | 選んだ元構成とペアで境界改善を比較 |
| D | Audio Separatorで分離＋Aと同じASR・照合 | Bに導入・精度・時間の問題がある場合に比較 |

AとBではモデル、デコード条件、VAD設定、照合設定を固定する。VADはまず無効で比較し、無音・器楽区間で認識の迷いが多い場合に両条件で有効版を追加する。比較条件の選択と調整は調整曲で行い、評価曲には固定設定を用いる。CPUとGPUの構成が異なる場合は結果と設定を別々に記録する。

## 照合の方式

1. 歌詞を行ID、入力順、表示原文に分け、既知の構成タグと空行を除外する。認識側では時刻付きのトークンまたはセグメントを保持する。
2. 比較用の表記キーをUnicode正規化・英字の大小統一・空白や句読点の整理で作り、読みキーをSudachiの読みとひらがな統一で作る。未知語、独自の読み、英語、長音は表記キーも残し、読みだけで決めない。
3. 時刻付きの連続した認識断片から行候補を作る。表記・読みの編集距離、対応した文字数、区間長を用いて候補を比較する。複数の認識断片にまたがる行と、同一断片内の複数行を扱う。断片より細かい時刻が得られない場合は推定であることを記録する。
4. 動的計画法で、時刻が後ろへ進む行対応を全体で選ぶ。入力行の欠落と認識断片の読み飛ばしを別の遷移にし、前奏・間奏・後奏を通過できるようにする。サビの同文行は個別のIDで評価し、前後の行と候補の順序を使う。
5. 対応断片の時刻から行境界を得る。代替候補との差、対応文字率、読み・表記の不一致、境界の粗さ、器楽区間への割当などを要確認の理由にする。根拠不足で時刻を提示できない行は未配置として扱う。表示する確からしさは照合の目安とする。
6. 強制アライメントでは、暫定行の近傍だけを探索し、近接行との逆転や語彙外文字率を確認する。十分な音響根拠がある境界を採用し、再推定に失敗した行は元の候補と警告を保持する。

## 評価素材と正解データ

- 使用を確認した日本語Suno楽曲を目安10曲用意し、調整4曲・固定評価6曲に曲単位で分ける。同じ曲の生成違いを異なる集合に入れない。速い歌唱、音量差、ハモリ、長い間奏、繰り返し、表記揺れ、歌詞の省略・追加が含まれるようにする。曲数と内訳を調整前に確定する。
- 固定評価では、先にシステムで同期とSRT出力を行い、自動チェックで行別の裏付けを確認する。使用者による全行の手動注釈を前提にしない。
- 独立した正解時刻が得られた場合は、最初と最後の聞き取れる歌唱音を基準に比較する。繰り返しは出現順にIDを付け、歌唱なしと判定保留を分け、判定保留の件数を報告する。
- SRT/JSONの入出力、タグ、順序、時間範囲、Windowsの日本語パスは合成フィクスチャで再現する。実曲・歌詞・認識全文・時刻付き正解はローカルに保持し、Issueには許可された集計と再現設定を載せる。

## 自動チェック

生成に使わなかった別サイズの認識モデルで原音を認識し、同じ歌詞に照合する。生成時刻との開始・終了の差、別モデルの文字対応率、字幕区間のボーカル活動率を記録する。両境界の差が500ms以内、文字対応率65%以上、活動率35%以上の行を「裏付けあり」とする。時刻があるものの基準から外れた行は理由を記録する。

曲別に時刻付与、裏付けあり、要確認、未配置を集計する。前後2秒の時刻ずれを意図的に加えた場合のモデル間一致数も確認する。各モデルは認識誤りを共有しうるため、これらは自動チェックの結果として報告し、既知の正解に対する時間誤差や実用行率とは分ける。

## 指標と移行基準案

| 指標 | 測り方・暫定基準 |
| --- | --- |
| 実用行率 | 評価対象の歌唱済み行を分母とし、正しい出現で開始・終了とも誤差が500ms以内の割合。評価6曲の曲別平均85%以上、各曲70%以上を提案する。未配置・誤った繰り返しは失敗。境界誤差の中央値/P90、未配置率、器楽区間への誤割当も併記する。 |
| 要確認の捕捉率 | 実用行率の測定で失敗扱いになった行と、原音で歌唱されないのに時刻が付いた行のうち、警告・未配置になった割合。80%以上を提案し、適合率と分母件数も報告する。 |
| 修正時間 | 最低2曲で同じ操作者が、白紙から付ける方法と同期候補を直す方法を同等のツールで比較する。完成基準を揃え、曲ごとに順序を入れ替え、曲を覚える影響を記録する。操作時間の中央値が手動比30%以上短縮を提案。自動解析の待ち時間は別集計。 |
| 実行負荷 | CPU/GPUごとに、前処理・分離・ASR・照合の経過時間、音源長に対する処理時間、ピークRAM/VRAM、エラーを記録。初回取得・キャッシュなし・キャッシュありを区別する。進行基準の運用上限は対象機と実測を見てレビューする。 |

暫定閾値は試験前に合意する。評価対象曲ごとに分母と結果を添え、少数の結果から日本語曲全般には外挿しない。確認用JSONには時刻候補と根拠を含め、SRTは有効な配置済み行を原文で出力し、除外行の件数を表示する。反復の取り違えや未配置に警告を出せること、CPUで完走することを確認する。GPUは利用可能な環境で別途確認する。

## 実施と判定

まずWindowsで依存関係と素材の読込を検証し、合成素材で境界と出力を確認する。調整曲でA/Bを回して条件を固定し、必要に応じてC/Dを加えて固定評価する。採用構成、残る課題、代表的な失敗と手直し時間を結果Issueにまとめる。基準を満たしユーザーが確認した時点でPhase 2に進む。満たせない場合は失敗を分析し、Phase 1内で別構成を試すか、対象範囲・操作フローの変更を相談する。
